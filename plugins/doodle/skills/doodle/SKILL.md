---
name: doodle
description: Use Doodle when a person wants to share visual context with the AI through a local infinite board, or asks to read, show, draw, or edit it.
---

Doodle is a two-way board shared by a person and an AI, not a chat product or project dashboard. Both can draw on the same canvas, read what the other drew, and continue from there. Use the three drawing tools through the Codex plugin or a direct MCP stdio connection. Doodle only reads and writes board state.

- First use is one sentence: 「打开 Doodle 画板，我们先用画板交流。」 Start with `get_board`; read `FIRST_USE`, `NEXT_STEPS`, `BOARD_JSON`, existing object IDs, coordinates, authors, the drawing guide, and the active local `PANEL_URL`.
- For an architecture discussion, draw a concise map from the information already present in the conversation. Mark uncertain relationships as questions and use Doodle to receive and preserve human edits.
- Use `show_board` when the person asks to see, open, display, or edit the canvas. After a successful `draw_board`, keep the canvas visible: compatible hosts render it from the draw result automatically; if the host does not, call `show_board` immediately. All tools remain usable in text-only hosts.
- Reread cheaply: pass `get_board.since_revision` with a revision you already hold to receive only changed objects plus `HANDOFF`, which lists what the person added, edited, or removed. It excludes your own writes, so use it instead of redrawing or asking the person to repeat themselves. The full guide is sent once per session; pass `include_guide: true` only when you need it again.
- After drawing, keep its returned revision as the baseline. After a person edits, use the embedded host's final board context when available; otherwise call `get_board.since_revision` with the revision from the board state you presented, usually the revision returned by your latest `draw_board`. Acknowledge the HANDOFF, preserve the person's labels, positions, and deletions, and continue with precise updates or additions. Do not reflow a collaboratively positioned board unless asked. Use `replace: true` only when they explicitly ask for a full redraw. Board edits never authorize or perform project file writes.
- Use `draw_board` for notes, text, rectangles, ellipses, and directed arrows. Put `author` at the top level, use short labels and a strict grid, and use `remove_ids` before redrawing a whole diagram. For a complex architecture diagram, prefer one `draw_board.diagram` call with semantic nodes and edges: it adds a deterministic bounded diagram beside existing objects, never mixes `diagram` with other mutation fields, and reserves `replace: true` for an intentional full redraw. Set `diagram.mode` to `timeline`, `compare`, or `matrix` when the explanation is ordered or tabular; those honour your explicit `column`/`row` instead of deriving them from edges.
- Use `draw_board.library` for editable named board snapshots: `list`, `save`, `switch`, `create`, `rename`, `duplicate`, `delete`, `import`, and `export`. Switching changes the single active board; `get_board` then reads that board. `export` returns editable version 1 JSON, never an image file.
- Image export belongs to the human canvas, not the MCP surface. When a person asks for a PNG, JPG, or SVG, point them at 图库 (Library) → 分享快照 → 导出 PNG / JPG / SVG in the embedded canvas or on `PANEL_URL`. Those are sharing copies for other people and never become board state or library entries. Do not answer that Doodle cannot export images.
- Before drawing, read `capabilities`, `visualDigest`, and `RECIPES` from `get_board`. Prefer short recipes: flow with `role: "step"` and `startItemId`/`endItemId`, compare with `role: "column"` or `variant: "frame"`, cluster with `groupId` and `layout.mode: "cluster"`, emphasis with `emphasis: "focus"`, and image annotation with bounded `image` plus connected lines.
- Optional version 1 fields `variant`, `role`, `z`, `style`, `startItemId`, and `endItemId` make drawings intentional without adding tools. Connected lines follow bound objects. Use deterministic `layout.mode` values `grid`, `row`, `column`, `timeline`, `cluster`, or `architecture`; when reflowing a board, pass `layout.ids` to select only the objects that may move, and leave human-positioned objects in place unless asked.
- A `line` is an arrow from `(x,y)` to `(x+w,y+h)`; `w` and `h` are signed endpoint deltas. Endpoints belong just outside the source and target shapes.
- `PANEL_URL` is a local human-facing address. Mention it when the person asks where to look or when the host cannot render an embedded canvas; never open a browser or editor from a normal tool call.
- The canvas `?` help button gives people the three gestures: choose a tool and click/drag, double-click to edit text, Space/wheel to move around. Press `?` to reopen it.
- In MCP Apps hosts that support `updateModelContext`, the embedded canvas automatically publishes the latest final board state and a final-state delta to the current host conversation's model context; it is not an operation log and does not trigger a turn. `通知 Agent` uses `sendMessage` only for one short user notification. In text-only hosts or on the standalone `PANEL_URL` page, ask the agent to call `get_board` after the person draws or edits.
- Conversation stays in the agent host chat. Board objects and notes are visual context; they never become approval credentials or project writes.
