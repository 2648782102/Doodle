# Doodle 绘图评测台设计（草案 v0.1）

> 状态：设计稿，未实现。目标读者是接下来要动手的人。
> 本文不改变任何产品契约；它描述一个**离线**评测环境。

## 1. 要回答的问题

现有测试都是「给定输入，断言输出」的契约测试：`first-try.test.mjs` 验证拒绝可修复，
`ai-experience.test.mjs` 验证 digest/diagnose 的形状，`sync-loop.test.mjs` 验证并发写入。
它们全部**不碰真实模型**，因此无法回答下面这类问题：

1. 让一个真模型画「订单履约的五个阶段」，它第一次就把图画对吗？
2. 模型画的图，人一眼看得懂吗？还是标签叠在一起、箭头穿过卡片？
3. 一次会话花多少时间、多少 token？换 `diagram` 与手填坐标，差多少？
4. 人改了 AI 的图之后，AI 下一次读回来能理解改了什么并接着画吗？
5. 换模型 / 换提示词 / 改工具描述，这些数字是变好还是变坏？

第 5 个问题是关键：**没有它，一切"感觉变好了"都是不可验证的。**

## 2. 为什么不能只比截图

图生图的像素对比（SSIM/CLIP）在这里会误导：同一张流程图，卡片挪了 20px、
换个色板，语义完全相同，但像素差异巨大。反过来，卡片全部重叠在一起时，
像素可能"很像"模板，却完全不可读。

业界做法（DiagramEval, ACL Findings 2025）是把图当**有向图**评分，而不是当图片：
节点、边、层级、拓扑顺序分别打分。这对 Doodle 特别合适，因为 Board v1 本来就存着
精确的 `x/y/w/h`、`startItemId/endItemId`、`role`、`emphasis`——**图的真值结构是现成的**。

所以评分分三层，从硬到软：

```
Layer A 结构（机器可判，无歧义）  ← 90% 的权重
Layer B 几何与可读性（启发式）    ← 用 Board 自己的 diagnose + 新写的判据
Layer C 语义（模型判分 + 人审）   ← 抽样，不做主判据
```

像素图只作为**报告附件**，给人看，不参与打分。

## 3. 工作流设计思路

借用 DAG 工作流的分层：**任务 → 执行 → 观测 → 判分 → 汇总**，每层可独立替换。

```
 ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
 │ 1 任务集 │ → │ 2 执行器 │ → │ 3 观测   │ → │ 4 判分   │ → │ 5 报告   │
 │  cases   │   │ driver   │   │ trace    │   │ graders  │   │ report   │
 └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
       ↑                                                  │
       └──────────── 6 人机回环（human-in-loop）───────────┘
```

### 为什么是"工作流"而不是"一个大脚本"

- 每个 case 相互独立，可以并行、可以单独重跑、可以只跑失败的。
- 执行器可替换：今天用真实 MCP 客户端，明天可以换成"离线模型回放"。
- 判分器可替换：结构判分是纯函数，语义判分才需要模型。
- trace 是唯一事实来源：报告、回归对比、人工复核都从它重算，不重复跑模型。

## 4. 五层具体设计

### 4.1 任务集（cases）

一个 case 是一份**声明式**的期望，不是一个脚本：

```jsonc
{
  "id": "flow/order-fulfilment",
  "prompt": "把订单履约流程画出来：下单 → 校验 → 拣货 → 发货 → 签收",
  "expect": {
    "kind": "sequence",              // sequence | tree | comparison | freeform
    "nodes": ["下单", "校验", "拣货", "发货", "签收"],
    "edges": [["下单","校验"], ["校验","拣货"], ["拣货","发货"], ["发货","签收"]],
    "ordered": true,                 // 顺序有意义，允许列优先/行优先两种排布
    "max_crossings": 0,
    "forbidden": ["重叠", "孤立"]    // 见 4.4
  },
  "budget": { "max_tool_calls": 3, "max_seconds": 60, "max_bytes": 80_000 }
}
```

任务集分四类，从易到难：

| 类别 | 例子 | 判分重点 |
|---|---|---|
| `sequence` | 五步流程、时间线 | 节点集合 + 边是否连通成链 |
| `tree` | 组织架构、目录树 | 父子关系正确，层级不交叉 |
| `comparison` | 方案 A/B 对比 | 列分组正确，不对齐也算错 |
| `freeform` | 「解释这段代码的结构」 | 只判可读性下限 + 人审 |

**关键要求**：`nodes` 用**归一化后的标签**匹配（去空白、去标点、允许同义前缀），
否则模型写"校验订单"会被判成缺失"校验"。

### 4.2 执行器（driver）

执行器只做一件事：把 case 变成一次真实的 MCP 会话，并记录 trace。

```
for each case (可并行, 默认并发 2):
  temp OUTPUT_DIR              # 每个 case 一张干净的板，互不污染
  spawn `node dist/index.js`   # 真实 stdio server
  connect MCP client
  t0 = now
  call model with: system(doodle 的 MCP instructions) + prompt + tools
  loop:
    模型选择工具 → 调用 → 记录 (tool, args, result, 耗时, 字节数)
    直到模型说完成 / 超预算
  t1 = now
  board = get_board(view:"full")
  png   = 可选的 canvas 截图（供人看，不入分）
  write trace.json
```

三条硬要求：

1. **必须用真实 server + 真实 MCP 客户端**，不能直接调内部函数。
   工具描述、schema 校验、`ERROR_JSON` 的可修复性都是被评对象。
2. **每次从空板开始**，`OUTPUT_DIR` 用临时目录，跑完保留以支持复现。
3. **记录重试**。模型第一次画错、看到 `ERROR_JSON` 后修好，这是**正面信号**，
   要和"一次就对"分开统计——否则修复能力会被算成失败。

### 4.3 观测（trace）

trace 是整个系统的地基。建议结构：

```jsonc
{
  "case": "flow/order-fulfilment",
  "model": "…", "prompt_hash": "…", "tool_desc_hash": "…",
  "started_at": "…", "duration_ms": 12345,
  "turns": [
    { "tool": "get_board", "args": {...}, "ok": true, "ms": 12, "bytes": 4800 },
    { "tool": "draw_board", "args": {...}, "ok": false,
      "error": { "code": "SIZE_OUT_OF_RANGE", "path": "items[2].w" } },
    { "tool": "draw_board", "args": {...}, "ok": true, "ms": 31, "bytes": 6400 }
  ],
  "usage": { "input_tokens": 0, "output_tokens": 0 },
  "final_board": { /* Board v1 */ },
  "budget_exceeded": false
}
```

`prompt_hash` 和 `tool_desc_hash` 很重要：**改了工具描述就是改了实验条件**，
没有它，两次跑的差异无法归因。

### 4.4 判分（graders）

每个判分器是纯函数 `(trace, expect) → {score, checks[]}`，可单独测试。

**结构判分（Layer A，权重最高）**

| 指标 | 定义 | 来源 |
|---|---|---|
| `node_recall` | 期望节点中被画出的比例 | 归一化标签匹配 |
| `node_precision` | 画出的节点里属于期望的比例（惩罚乱加） | 同上 |
| `edge_f1` | 期望边集合 vs 实际边集合的 F1 | `startItemId/endItemId` |
| `sequence_ok` | 有序任务里，边的方向是否构成单链（无环、无分叉） | 拓扑检查 |
| `level_ok` | 树任务里，父子深度是否与期望一致 | 从边推导 BFS 深度 |

这一层**完全不需要模型**，也不会漂移，适合进 CI 做阈值门禁。

**几何与可读性（Layer B，启发式）**

复用现有 `diagnoseBoard()`，再补几个它没有的：

| 指标 | 定义 | 现状 |
|---|---|---|
| `no_overlap` | 节点两两不重叠 | ✅ `diagnose.overlapping` |
| `no_isolated` | 无孤立节点 | ✅ `diagnose.isolated` |
| `no_dangling` | 无悬空连接 | ✅ `diagnose.unresolved` |
| `edge_crossings` | 连线交叉次数 | ❌ 需新写（线段求交） |
| `edge_through_node` | 连线穿过无关卡片 | ❌ 需新写（线段-矩形相交） |
| `label_fit` | 文本是否超出卡片 | ❌ 需新写（估算文本宽度） |
| `density` | 画布面积利用率（太挤/太散都扣分） | ⚠️ 有 `bounds`，需补阈值 |
| `aspect_ratio` | 整体宽高比是否适合屏幕 | ⚠️ 可由 bounds 推导 |

`edge_crossings` 和 `edge_through_node` 是最能反映"图看着乱"的两项，
也正是现在完全没有测的。这两项应当优先实现。

**语义（Layer C，抽样）**

不做主判据。用两个廉价信号：

1. **模型判分**：让另一个模型看「期望 labels + 实际 digest」给 1–5 分，
   只用于发现"结构对但语义错"的 case（例如把"拒绝"画成了"通过"）。
2. **人审**：每个 case 留一张 PNG，抽样 10% 人工过一遍。

语义分**不进 CI 门禁**——它会漂移，且成本高。

### 4.5 报告（report）

输出一份 Markdown + 一份 JSON：

```
按 case 类别汇总：
  sequence    n=12  node_recall 0.94  edge_f1 0.88  一次通过率 58%
  tree        n=6   level_ok 0.75    crossings 1.2/case

失败聚类（最有用的部分）：
  - 5/12 的 sequence case 出现了 edge_through_node
  - 3/6 的 tree case 层级深度错了一级
  - 2 个 case 首次调用被 SIZE_OUT_OF_RANGE 拒绝，重试后成功

与基线对比（同一份 cases，diff 上一版）：
  edge_f1       0.88  (↑0.06)
  crossings     1.2   (↓0.8)
  一次通过率    58%   (↑11pp)
```

**"失败聚类"比总分更有价值**——它直接告诉你下一步该改什么。

### 4.6 人机回环（第 6 层，也是你说的重点）

这是 Doodle 独有、也是最难自动化的部分。建议拆成**三步递进**，不要一次做完：

**第一步：脚本化的人（可自动）**

用代码扮演"人"：在 AI 画完后，对板执行固定的修改——
移动一个卡片、改一个标签、删一条边——然后让 AI `get_board(since_revision)`。
判定：AI 的 `HANDOFF` 是否**正确识别了这次修改**（改的是哪个、改成了什么）。

这可以完全自动化，且是真正的双向性测试，现有测试里没有。

```jsonc
"human_action": { "type": "move", "label": "拣货", "dx": 200 },
"expect_ai": { "detects": ["拣货"], "continues": true }
```

**第二步：真实浏览器的人（半自动）**

用已有的浏览器自动化（`browser-contract.test.mjs` 已经会驱动画布）
执行真实的拖拽和编辑，截图，然后同样判定 AI 的读回。
好处是走真实 `POST /batch` 路径，能抓到画布投影层的 bug。

**第三步：真人（不可自动）**

一个最小的"人机接力"脚本：跑一个 case，打开画布给人看，
人改完按回车，脚本继续让 AI 读回。产出一份主观评分表
（可读性 1–5、AI 是否理解我的修改 是/否）。
**这一步只做季度抽检，不进 CI。**

## 5. 与现有测试的关系

| 现有 | 新评测 |
|---|---|
| 纯函数、无网络、毫秒级 | 真实模型、真实 MCP、分钟级 |
| 进 CI，每次提交必跑 | **不进默认 CI**，按需/夜间跑 |
| 断言精确输出 | 输出分布性指标 |
| 防回归 | 找方向 |

明确边界：**benchmark 不替代契约测试**。契约测试防"改坏"，
benchmark 答"哪种改法更好"。两者目标不同，不要混进同一个 suite。

## 6. 实施顺序（建议）

按"先能判分，再能跑模型"的顺序——判分器是纯的，可以先写、先测、先稳定。

1. **判分器 + 快照回放**（无模型，1–2 天）
   写 `node-structure` / `edge-f1` / `crossings` 几个纯函数，
   用手写的 board 快照做输入，完全可单元测试。**这一步不需要任何 API key。**
2. **trace 格式 + 回放器**
   定义 trace schema，写一个"从 trace 重算报告"的命令。
3. **执行器接入一个模型**
   先跑 3–5 个 case，确认能跑通，再看数字有没有意义。
4. **扩充 cases 到 30 个左右**，分四类。
5. **人机回环第一步**（脚本化的人）。
6. 视情况做 4.4 的 Layer C 和 4.6 第三步。

## 7. 几个容易踩的坑

- **别用像素比图**。理由见第 2 节。
- **别让语义判分进 CI**。它会漂移，而且"看起来对"不等于"结构对"。
- **别把重试算成失败**。模型看错误信息修好，正是 Doodle 设计目标的体现。
- **工具描述变了要重跑基线**。`tool_desc_hash` 变了，历史数字就不可比了。
- **每个 case 用独立 OUTPUT_DIR**。否则 `library` 的种子板会串味。
- **固定随机性**。模型 temperature、并发顺序、超时都要记进 trace。
- **成本要记账**。一次 30 case × 3 模型的跑批可能几十美元，报告里要有估算。

## 8. 未决问题

- 判分阈值定多少才算"通过"？建议先跑 20 次基线，取 P50 作为初始门禁。
- 语义判分用哪个模型？用被测模型判自己会偏向自己。
- `freeform` 类怎么判？暂时只判可读性下限，不判"内容对"。
- 是否需要保存 PNG？存储成本低、便于人审，建议保留但**不入分**。

## 9. 第一步已落地：判分器（`bench/graders/`）

设计里最容易空转的是"判分到底靠不靠谱"。所以先把**不需要 API key** 的那层做出来了，
它现在就是可用、可测的代码：

```
bench/graders/normalize.mjs   标签归一化与匹配
bench/graders/structure.mjs   节点 / 边 / 序列 / 树
bench/graders/geometry.mjs    交叉、穿卡片、密度、悬空连接
bench/graders/index.mjs       汇总成 score + checks + pass
bench/graders/graders.test.mjs 17 条测试
```

### 它已经能区分好坏

用真实 `draw_board.diagram` 生成的板做对照（`test` 里也有同样的断言）：

| 情形 | score | pass | 指出的问题 |
|---|---|---|---|
| 五步完整流程 | 1.00 | ✅ | — |
| 少画一步 | 0.89 | ❌ | `node_recall`, `edge_f1` |
| 中间两步顺序颠倒 | 0.66 | ❌ | `edge_f1` |
| 多画无关节点 | 0.98 | ❌ | `node_precision` |
| 链条断开 | 0.74 | ❌ | `edge_f1`, `sequence` |
| 箭头绑到不存在的对象 | 0.74 | ❌ | `dangling` |
| 空板 | 0.00 | ❌ | 全部 |

注意"顺序颠倒"拿到 0.66 而不是 0：节点都在、边也画了，只是有一对方向相反。
这正是想要的行为——**分数反映错误的严重程度，而不只是二元的对错**，
报告才能告诉你"差在哪"。

### 一个有意的设计取舍

`pass` 要求结构完全正确，但 **`crossings` / `density` 默认不导致失败**，
只有 case 显式写了 `expect.forbid` 才生效。理由：一张完全正确的流程图，
偶尔有一条线交叉，不应该被判定为"AI 画错了"——那是排版噪声，不是语义错误。
几何分数照常记录，供人看趋势，但不制造假阳性。

## 10. 第二、三步已落地：trace、报告、执行器

### trace 与报告（无成本，可重复）

```
bench/trace.mjs         trace 形状 + 校验 + 稳定的短哈希
bench/report.mjs        判分汇总、失败聚类、两次运行对比
bench/run-report.mjs    CLI：trace 目录 → Markdown / JSON 报告
bench/cases/core.json   3 个真实 case
bench/fixtures/         3 份示例 trace（由真实生成器造板，不调用模型）
```

报告的样子（对着 fixture 跑出来的真实输出）：

```
Cases: 3 · pass 33% · mean score 0.83

## Failure clusters
- edge_f1 — 2/3 cases (sequence 2)
- node_recall — 1/3 cases (sequence 1)
- sequence — 1/3 cases (sequence 1)

## Repair behaviour
1/3 cases saw at least one rejected call and continued.
These are repair successes, not failures.
```

「2/3 卡在 edge_f1」直接指向连接线生成，比「平均 0.83」有用得多。

两个刻意的保护：

- **trace 缺 `final_board` 直接报错**，不判成空板。"模型没画"和"记录器丢了板"
  是两种完全不同的结论，混在一起会污染均值。
- **prompt 或工具描述变了就拒绝给 delta**，并说明"这应当视为新基线"。
  否则会打印一个看着很确定、实际不可比的数字。

`1/3 需要重试` 被单独统计为**修复成功率**，不计入失败——模型看到 `ERROR_JSON`
改对，正是 Doodle 设计目标在起作用。

### 执行器（需要真实模型）

```
bench/executor.mjs      spawn `codex exec`、解析 JSONL 事件、写 trace
bench/run-cases.mjs     CLI：跑 case → traces/
```

执行器本身很薄，但做了三处隔离，每一处都是实测踩出来的：

1. **用临时空目录当工作区**。仓库自己的 `AGENTS.md` 有 48 KB，超过 Codex 的
   32 KB 项目指令预算，模型会收到截断版并花一个回合去注意这件事——那测的是
   仓库，不是绘图。
2. **`--ignore-user-config`**。本机装了一个无关的 doodle 插件，模型会先去读它的
   skill 文件再调工具。基准必须只看到被测的那个 server。
3. **每个 case 独立 `OUTPUT_DIR`**，否则 library 的种子板会串味。

### 一个值得记下来的坑

第一次跑批，trace 里 0 次工具调用、0 token，耗时 126 秒。看起来像"模型拒绝作画"。

实际原因是 `codex exec` 会等 stdin EOF 才发 prompt，而 `spawn` 用了
`stdio: "ignore"`，描述符永远不到 EOF，于是挂到超时。

修法是把 stdin 改成 `pipe` 然后立即 `end()`。同时加了一条守卫：
**没有工具调用且没有 usage 的 session 一律判为失败并说明原因**，
因为它只可能意味着请求没到达模型（网络/鉴权），而不是模型什么都没画。
这条守卫让"环境坏了"和"模型不行"在报告里永远不会混为一谈。

### 当前状态

`bench/graders` 17 条 + `bench/report` 15 条 + `bench/executor` 7 条测试，
共 39 条，全部不需要模型。真实跑批需要能访问模型的网络环境：

```

```

## 11. 已接入真实模型，并跑出第一份基线

### 接入方式：magpie 网关

本机直连模型厂商被阻断（`api.openai.com` 超时），但 magpie 的本地网关
`127.0.0.1:3425` 可用。执行器因此固定走：

```
-c model_provider="magpie"
-c model_providers.magpie.base_url="http://127.0.0.1:3425/v1"
model = workbuddy/blind-model-c   （「测试模型 C」）
```

`--ignore-user-config` 会把用户配置里的 provider 一并去掉，所以网关配置必须在
命令行里重述一遍；`name` 字段不能省，否则 CLI 直接拒绝整个配置。

### 一个拦路的坑：破坏性工具需要审批

第一次真跑，3 个 case 全部「成功但板是空的」。模型确实调了 `get_board`，
但 `draw_board` 被宿主拒绝：

```
MCP tool call requires approval, but approval policy is never
```

`draw_board` 声明为破坏性工具，`--sandbox read-only` 下审批策略是 never。
改用 `--dangerously-bypass-approvals-and-sandbox` 后正常——进程本就跑在临时目录、
只连本地 stdio server、提示词禁止碰文件，隔离是够的。

### 第一份真实基线（10 个 case，模型 C）

修完判分器后：

```
Cases: 10 · pass 100% · mean score 1.00

| category   | n | score | pass | node recall | edge F1 |
| sequence   | 8 | 1.00  | 100% | 1.00        | 1.00    |
| tree       | 1 | 1.00  | 100% | 1.00        | 1.00    |
| comparison | 1 | 1.00  | 100% | 1.00        | 1.00    |
```

**这个结果本身说明下一件事：case 太容易了。** 满分不是好消息，
它说明当前这 10 个 case 无法区分模型好坏。真实的待办是加难度，
而不是庆祝。

### 判分器被真实数据修正了四次

这是先做判分器、再接模型的价值——每一次都是**判分器错，模型对**：

1. `precision 0.6`：生成器自带的 frame / title / subtitle 被当成节点。
2. `recall 0`：模型写「1 注册 / 登录：创建账号…」，而期望是「注册」，
   前缀匹配判为缺失。
3. `edge_f1 0`：对比类图没有边，却被按「缺 4 条边」计分。
4. `extra: ['六个阶段按顺序流转']`：副标题没逗号，逃过了标点规则。

每一条都补了测试。**判分器的假阳性/假阴性比模型分数更危险**，
因为它会把方向错误包装成数字。

### 人机回环（双向性）

```
bench/human-loop.mjs       脚本化的人：移动 / 改名 / 删除
bench/run-human-loop.mjs   真跑：AI 画 → 人改 → AI 读回
```

判分不看措辞，看两件事：**有没有指出被改的那个对象**，以及
**有没有编造板上不存在的对象**（后者比漏掉更严重——模型会对着不存在的东西画）。

第一次真跑（模型 C）：

```
board : 计划 → 执行 → 复盘
人   : 把「执行」移动 (260, 140)
HANDOFF: 人改动了 1 处：新增 0 · 修改 1 · 删除 0
模型 : 他们改动了「执行」卡片，把它从原位置向下拖到了 (560, 260)，移到「复盘」下方。
判分 : PASS（识别 1，遗漏 0，编造 0）
```

这是 Doodle 相对一次性图表生成器的核心差异，之前完全没有测试覆盖。

## 12. 加难度、多模型并行、人机回环扩全

### 难度：从 100% 降到 88%

上一轮 10 个 case 全部满分，说明**区分度为零**。新增 7 个更难的 case
（`bench/cases/hard.json`）：分支汇合、三层依赖、带环回退、十步长链、
带约束标注、两组对比、密集状态机。

同一模型（C）在 17 个 case 上的结果：

```
pass 88% · mean score 0.96
```

唯一的失败是 `flow/onboarding`：模型画了「完善资料」，而 case 期望「验证」。
这是**真实的内容差异**，不是测量噪声——基准的价值就在这里。

### 多模型并行

```
node bench/run-matrix.mjs --models m1,m2,m3 --concurrency 3
node bench/run-report.mjs bench/runs/<dir> --per-model
```

两个维度的并行：**模型之间**并行（一次比较等于最慢模型的时间），
**模型内部**按 `--concurrency` 控制并发。安全性来自既有的隔离——
每个 run 有独立临时目录和独立 `OUTPUT_DIR`，两个模型同时画也不会串。

报告新增：

```
## By model
| model | cases | score | pass | node recall | edge F1 | ... |

### Per case
| case | model-a | model-b | model-c |
```

逐 case 矩阵是必要的：模型级均值会掩盖差异的形状——一个模型可能全错难题、
另一个全错长链，均值一样。

### 上游繁忙：必须重试，不能记为失败

真跑时模型 A 和 B 全部失败，初看像「这两个模型不会画」。实际是上游返回：

```
WorkBuddy: the model provider is temporarily unavailable (busy: you can retry)
```

第一次的重试判断只匹配抛出的 message，而「busy」在 stderr 里，所以没触发，
13 个不可用的 run 被记成 13 张画坏的图。现在识别 provider-busy 并以递增退避
重试三次。

**并行会放大这个问题**：并发越高越容易撞上繁忙。这条不是可选项。

### 人机回环扩到三种编辑

```
node bench/run-human-loop.mjs --edit move|relabel|delete
```

| 编辑 | 难度 | 实测 |
|---|---|---|
| move | 最易，HANDOFF 直接点名 | PASS |
| relabel | 位置不变、只有含义变了 | PASS |
| delete | 对象已消失，无处引用 | PASS |

删除相关的两个 bug 都是 harness 的，不是模型的：

1. **删节点没删连线**：残留的 line 指向已删除的 id，`parseBoard` 判定整板损坏，
   服务端隔离文件并从空板启动。模型如实说「板上有零个对象」，判分器却记成
   「没理解删除」。人删卡片时连线也会一起消失，所以修法同时也更真实。
2. **判分器只在 `after` 里找标签**：被删对象已经不存在，正确答案永远无法被
   识别。改为回退到 `before`，并让「编造」检查接受两侧的标签。

### 判分器又被修正了六次

加难度会立刻暴露判分器的粗糙之处。这一轮的六处，全部是「正确的图被判错」：

| 现象 | 原因 |
|---|---|
| `score 1.00` 但 `pass false` | 重叠检测有自己的节点过滤，把标题算进去 |
| 多余节点「方案对比」「决策与约束」 | 短标题被当成内容 |
| 多余节点「选择上线」「选择暂缓」 | `role: annotation` 是连线标签，不是节点 |
| 多余节点「从需求发布到新员工入职的完整链路」 | 副标题太长，长度/关键字规则都漏 |
| 注释类内容被判多余 | case 需要能声明 `expect.allow` |
| 一条无关节点的自由文本被静默吞掉 | 副标题规则太宽，把真实内容也排除了 |

最后两条方向相反，说明**判分器不能只朝一个方向收紧**：排得太狠会吞掉真实内容，
放得太松会把装饰算成内容。所以每一处都补了一对测试（该排除的排除、该计入的计入）。

## 13. 五个测试模型跑出真实区分度

magpie 上有 9 个测试模型，探测后 5 个可用（A/B/D/G 上游繁忙，I 参数被拒过一次）。

```
node bench/run-matrix.mjs --models workbuddy/blind-model-c,e,f,h,i --concurrency 4
```

5 模型 × 17 case = 85 次运行，并发 4，**约 5.5 分钟**。

### 结果

| 模型 | score | pass | node recall | edge F1 | median ms |
|---|---|---|---|---|---|
| E | 1.00 | **100%** | 1.00 | 1.00 | 33.5s |
| H | 0.96 | 82% | 0.97 | 0.95 | 28.3s |
| C | 0.95 | 88% | 0.99 | 0.93 | 29.5s |
| F | 0.94 | 76% | 0.88 | 0.93 | 48.9s |
| I | 0.84 | 71% | 0.84 | 0.82 | 77.9s |

**这是基准第一次具备真实区分度**：通过率跨度 71%–100%，且排序稳定。
注意 E 的 `edge F1` 也到了 1.00，而 I 慢了 2.3 倍——速度差异同样可测。

### 逐 case 矩阵揭示的差异形状

只看均值会得出「H 和 C 差不多」的结论（82% vs 88%），但矩阵显示：

- E 在 `hard/constraint-labels` 全对，C/H/F 都错
- I 在 `flow/onboarding` 和 `flow/review-loop` 全错，其他模型全对
- F 在 `compare/two-options` 和 `hard/two-groups-contrast` 都错

三个模型各有自己的弱项，修同一处不会改善另外两个。这正是逐 case 矩阵的价值。

### 判分器又被修正了五次

难 case 暴露的仍是「正确的图被判错」，且这次都来自**不同模型的画法差异**：

| 现象 | 模型做法 | 修正 |
|---|---|---|
| 三层架构 recall=0 | 空白卡片 + 卡片外的 `label` 写层名 | 与卡片重叠的 `label` 算卡片名 |
| 对比图缺「现状/目标」 | 分组标题放在 column 容器顶部 | 容器顶部的短文本是组名，不是大标题 |
| 多余节点「依赖」「通过」 | 连线旁放独立文本当边标签 | 距连线 48px 内的短文本是边标签 |
| 多余节点「连接：是 · 否」 | 把边标签罗列成图例 | 图例匹配时把边标签也算进去 |
| `branch-merge` 多一条边 | 用中间节点「汇合」代替直连 | case 声明 `allow`，边结构容差由 case 决定 |

第五条值得单独说：**没有一种画法是错的**。直连两个分支汇合，和画一个汇合节点，
语义相同。基准不能替人决定审美，所以允许 case 声明可接受的额外结构。

### 当前状态

```
pass 82% · mean score 0.93 · 5 models · 84 graded runs
```

剩余失败经逐条核对，全部是真实内容差异（例如模型画「完善资料」而 case 要「验证」）。

## 14. 交叉评审：模型 C 读别人的图

结构判分能回答「图对不对」，回答不了「这是不是人想要的东西」。两者的差距在实测中
很具体：`hard/constraint-labels` 要求每个分支带约束，某个模型把约束写进了**连线标签**
（`是 · 约束：需停机 2 小时`）——这是正确甚至更好的画法，但结构判分要求约束是独立节点，
判它失败。评审模型看着同一张图，给了 95 分。

所以加了第三层，但它不是「再算一遍结构分」：

```
bench/human-judge.mjs        把板渲染成可读文本、评审 prompt、结果解析、对账
bench/run-cross-review.mjs   生成者 × 评审者 的矩阵
```

### 三条硬规则

1. **评审者看不到结构分**。看不到，才谈得上独立验证。
2. **评审者看不到是谁画的**。否则它评的是模型，不是图。
3. **分歧是产出，不是错误**。结构判失败而评审通过，说明 case 写窄了——
   这是基准自己的 bug，也是这一层最有价值的产出。

### 对账分五类

| 类别 | 含义 | 该做什么 |
|---|---|---|
| `agree-pass` | 都说过 | 无事 |
| `agree-fail` | 都说错 | 失败是真的 |
| `judge-saves` | 结构判错，评审说对 | **去查 case，多半太死板** |
| `judge-stricter` | 结构判对，评审发现语义错 | 坐标检查看不到的问题 |
| `unknown` | 回复无法解析 | 不猜，如实报告 |

### 第一次真跑就抓到一个真 bug

```
compare/two-options  f 画 ← c 评   judge-saves
结构 0.75 fail / 评审 100 pass
```

模型 f 把一个方案画成「方案 A」盒子在上、「优点…」盒子在下。结构判分把
`role: label` 的**矩形**当成了标题排除掉，于是两个方案都没了。
评分从 76% 修到 82%，整体从 82% 到 85%。

这条 bug 用人眼看不出来——它在两种画法之间，只有交叉对照才会暴露。

### 分层的话，各自负责什么

| 层 | 能回答 | 不能回答 | 成本 |
|---|---|---|---|
| 结构判分 | 图对不对（确定性、可重放） | 是不是人想要的 | 0 |
| 评审模型 | 语义对不对、缺什么、冗余 | 精确的拓扑 | 每图一次调用 |
| 真人 | 一切 | 规模 | 不可行 |

**结构分仍是主判据**，评审是旁证。把评审当主判据会让基准变成「模型的品味」，
而且会漂移——这正是第 4.4 节明确拒绝的做法。

### 抽样必须分层，否则白跑

第一次跑用 `--limit 2` 直接取前两个 case，结果 30 条全是 `agree-pass`——
好模型的输出本来大部分就是对的。现在选择顺序是**结构判分先失败**，
预算内再填通过项。

### 已知局限：同义词

```
期望: 注册 / 验证 / 引导 / 首次使用
模型: 新用户注册 / 账号激活 / 新手引导 / 首次使用
```

评审说「四个阶段均已完整画出」，人看着也同意；字符串匹配判 recall 失败。
这是结构判分的固有局限，**不打算靠同义词表解决**（表会无限膨胀且不可解释）。
它在报告里表现为 `judge-saves`，由人决定是修 case 还是接受差异。

## 15. 重复采样推翻了上一轮的排名

单次运行的排名不可信。3 模型 × 17 case × **3 次** = 153 次运行，并发 5，
752 秒（约 12 分钟）。

### 置信区间全部重叠

```
模型    attempts  pass (95% CI)      node recall  edge F1  median
E       51        86% (74%–93%)      0.99         0.97     64.0s
H       51        82% (70%–90%)      0.98         0.95     58.2s
C       51        86% (74%–93%)      0.97         0.94     57.6s
```

上一轮单次采样给出的排序是「E 100% > C 88% > H 82%」，看起来有清晰差异。
**重复采样后三个区间完全重叠，这个排序不成立。**

这是重复采样唯一的、也是最重要的产出：它把上一轮那个"看起来很有说服力"的结论
证伪了。如果只跑一次就对外报排名，报的是一个噪声。

### 14 个 case 在同一个模型上时对时错

```
C · hard/review-with-rollback  1/3
E · compare/two-options        1/3
H · flow/onboarding            1/3
C · flow/onboarding            2/3
...
```

「时对时错」和「稳定地弱」是两件事，对使用者的意义完全不同：

- 稳定地弱 → 这个模型不会做这类图
- 时对时错 → 它会做，但不确定；同一个人问两次可能得到不同质量

报告把两者分开列，因为只看均值会把它们混成一个数字。

### 抽查：同一模型三次三种画法

`hard/review-with-rollback`，模型 E 的三次尝试：

```
#1  提交→评审  评审→发布  发布→验证  验证→回退→评审   （多画了一个「回退」节点）
#2  提交→评审  评审→发布  发布→验证  验证→评审        （正确）
#3  提交→评审  评审→发布  发布→验证                   （漏了回退边）
```

这不是判分器的问题，也不是 case 写错——**模型自己不稳定**。第三次漏掉的分支，
正是这个 case 唯一想测的东西。

### 为什么要 Wilson 区间而不是 ±1.96σ

正态近似在这里不可用：`3/3` 会算出零宽度、宣称确定；通过率接近 1 时会跑出 100% 以上。
Wilson 区间始终落在 `[0,1]`，且样本小的时候自动变宽——这正是重复采样要表达的不确定性。

### 结论怎么用

| 想回答 | 需要几次采样 |
|---|---|
| 这个模型能不能画这类图 | 1 次够（失败即不能） |
| 两个模型谁更强 | **≥ 3 次**，且看区间是否重叠 |
| 这次改动是否有改善 | 同 case 同模型，前后各 3 次对比 |

单次运行只适合发现「明显的不能」，不适合排序。


## 16. Token 成本：先量清楚，再动手

「294K input token 一次运行」这个数字很吓人，但它几乎不是 Doodle 的账。把它拆开：

```
Codex CLI 自身的系统提示        约 40,400 tok
Doodle 的四个工具定义           约  5,100 tok
  └ draw_board 一项              约  4,350 tok（85%）
单次画图的真实新增               约  1,640 tok
```

`bench/measure-context.mjs` 就是量这件事的：同一句 "reply OK"，只换工具列表，
直接打 provider 看 input token。**任何 schema 或描述的改动，合入前都能先算成本。**

### 缓存改变了一切

一次完整画图会话实测：

```
total 82,921  cached 81,280  fresh 1,641
```

第二次运行几乎相同。也就是说 **Doodle 的工具定义在缓存里，每轮只付 1.6K 新增**。
这决定了两件事：

1. 削减 schema 的收益**低于**按总量估算的样子——它只在缓存未命中时全额付一次。
2. 真正该压的是**每轮新增**：模型调用几次、每次带多少内容，而不是定义有多长。

### 已经做了的削减

把四处重复的 `switchTo` 说明合成一句常量，`diagram` 与 `itemInput` 的描述去掉
重复的边界声明（边界已由 `capabilities.limits` 发布）。

```
固定成本  5,103 → 4,687 tok  (−8%)
schema    14.7 → 11.9 KB    (−19%)
```

### 剩下的空间在哪里

拆开 `draw_board` 的四个字段：`items` 829 tok、`diagram` 796、`library` 667、
`updates` 1,121。**没有单一字段能大幅削减**——要去更多，只能改工具设计
（例如把 `library` 拆成独立工具），而那是产品决策，不是优化。

去掉全部描述后结构骨架仍是 2,440 tok，所以「继续压描述」的上限很低。

### 通过率：这一轮的改动没有可信结论

把「不要加图例、不要把连线标签写成独立文本」加进 read guidance 后，跑了
2 模型 × 17 case × 2 次：

```
E  94% (80–98)   之前 86% (74–93)
H  72% (55–84)   之前 82% (70–90)
```

一升一降，且样本只有 32 次、区间极宽。**这不能证明改动有效**。
要判断这类提示词改动的收益，需要每个 case 5 次以上，或直接对比
「加引导 vs 不加引导」两批同样规模的运行。这一轮没做，所以不声称结论。


## 17. 轮次才是成本与准确率的主导项

上一轮把 token 拆开之后，问题变成「什么在决定每轮成本」。答案不是定义长度，是**轮次**。

对 153 次运行做工具序列统计：

```
54x  draw_board                      （35%，理想路径）
15x  get_board → draw_board
13x  draw_board → draw_board
 8x  get_board → get_board → draw_board → draw_board
 7x  draw_board → draw_board → draw_board
...
```

平均 3.12 轮。**65% 的运行有多余轮次。**

### 多出来的轮次在修几何

73 次运行画了两遍以上。看第二次 `draw_board` 改了什么：

| 改的字段 | 次数 |
|---|---|
| `x,y,w,h` / `w,h` / `y` 等几何 | **~40** |
| `text` | 3 |

模型**内容一次就写对了，位置和尺寸算不准**——因为它在手算坐标。

### 用 diagram 的画法少 3 倍轮次

| 方式 | 运行数 | 平均轮次 |
|---|---|---|
| `diagram`（自动布局） | 81 | **1.63** |
| 手写 `items` 坐标 | 72 | **4.81** |

这不是模型能力差异，是**任务形状**差异：手算坐标时模型必须反复微调。

### 改了什么

把「画两个以上互相关联的对象就用 `diagram`」从建议提到默认，并写明实测数字：

- `draw_board` 描述的第一句就说这件事，并给出 1.6 vs 4.8 轮的对比
- `get_board` 的 read guidance 增加同一提示（因为读在画之前）

`scripts/repo-check.mjs` 锁定了描述里的三个关键短语，我调整顺序时被拦下过一次——
它挡住的是「把已有信息删掉」，这次要求在，是对的。

### 结果

case 集同时从 17 扩到 38（新增 21 个更常规的序列/树/对比场景）。

```
平均轮次        3.12 → 2.31（−26%）
中位耗时        57–64s → 44–51s
通过率          85% → 93%
```

通过率提升有一部分来自 case 集变化（新 case 更常规）。所以另做了一次**只比共同 case** 的对照：

```
34 组共同 case：3.99 轮 → 2.36 轮（−41%）
```

**这个 41% 是干净的**——同样的 case、同样的模型，只换了引导。这才是这一轮的结论。

### 为什么这比压 schema 重要

schema 削减只省 373 token（−7%），而且多数在缓存里。轮次少一轮，就少一整份上下文 + 一次往返：

```
3.12 → 2.31 轮，每轮约 1.6K 新增
≈ 每张图少 1.3K 新增 token，外加一次网络往返
```

轮次的收益是复利式的，token 削减是线性的。
