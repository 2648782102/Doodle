## 通用红线

所有目标共享以下约束，各目标的正文不再重复：

- 当前 MCP 只提供 `get_board`、`show_board`、`draw_board` 三个工具；不做第二套会话模型、第二份持久状态或第二套画布引擎。
- 画板对象只是视觉上下文，永远不获得项目写入权限，也不构成审批凭据。
- 不新增任何会自动打开浏览器、IDE 或外部应用的工具副作用。
- 不做托管服务、多用户、账号、CDN 资源或遥测。
- 不 force push、不改写历史、不移动 tag、不删除用户画板数据。
- `stdout` 只走 MCP JSON-RPC，日志一律写 `stderr`。
- 人类画布的行为是回归面：任何让画布渲染变差的改动，即使节省 token 也算失败。

## 1. 基础闭环

### 目标

让核心回路稳定到"无聊"的程度：AI 一次语义请求就能画出一张可读的复杂图；人在**同一张** Excalidraw 画布上看见并修改；AI 读回最终状态后继续画；本地图库能保存和切换可编辑快照；内嵌 MCP App 保持终态上下文同步和一次「通知 Agent」提醒。Board v1 始终是唯一权威状态。

```text
get_board → draw_board.diagram → Board v1 → Excalidraw 投影
  → 人修改 → 版本安全的 Board v1 → get_board / 模型上下文 → 继续画
```

### 验收

- 当时版本的四个 MCP 工具、一份 version 1 状态格式。（这是 0.8.0 发布时的历史验收；当前工具面以目标 10 为准。）
- `draw_board.diagram` 接受有界的语义节点/边，默认在现有对象旁追加一张确定性图；`replace: true` 才清空重画。混合多种写入、重复节点 ID、未知边端点必须被拒绝。
- `layout.mode: "architecture"` 能对现有连接对象重排，标签有界、连线坐标稳定。
- Excalidraw 每次渲染都从 Board v1 派生，不存在独立的 scene 文件或 scene 端点；可选 `scene` 元数据只用于保留人手编辑的保真度。
- 形状内文字、独立文本、箭头标签、z 序、图片文件、绑定箭头，经过「AI 画 → 人改 → AI 读」不重叠、不被裁切。
- 内嵌宿主通过 `updateModelContext` 收到终态；「通知 Agent」只在宿主同时支持 `message.text` 时出现，且只发一句短消息。
- 图库支持保存、切换、重命名、复制、删除、导入、导出可编辑 version 1 快照；切换后画布与 AI 状态同步刷新。
- 文档、测试、CI 与离线守卫描述并验证同一套契约，`npm run check` 通过。

## 2. AI 视觉体验

### 目标

在不增加工具数量、不碰 UI 层的前提下，让 AI 仅凭 `get_board` / `draw_board` 的输入输出就能看懂画板、表达意图、纠正错误、解释自己改了什么。

### 验收

- 工具名与总数不变，不新增会话、消息或代码写入能力。
- `get_board` 提供确定性的视觉诊断：孤立节点、重叠、焦点、可放置空间，全部有界且无副作用。
- 写入失败返回 `ERROR_JSON`，含 `code` / `path` / `expected` / `fix`，模型可据此自行修正。
- `draw_board.diagram` 支持高层 recipe，AI 不必手算几十个坐标。
- 每次写入后，AI 能从返回里回答"改了什么"（`CHANGE_JSON`）。
- 存在 prompt contract 测试，模拟"AI 只看工具输出完成任务"。
- `capabilities` 固定 `role` / `emphasis` 的语义，不只是外观。
- `get_board` 支持分级读取 `summary` / `structure` / `detail` / `full`；降级只减 token，不改变权威状态。

**实测**：七项全部在当时的 MCP 工具内交付，`npm run check` 通过，端到端 MCP 会话走完六个检查点，未修改任何 UI 文件。

## 3. 原生视觉表达

### 目标

从"AI 能放对象"走到"AI 能用 MCP 工具表达和修订视觉想法，并且人能自然看懂、自然重塑"。保持一张 version 1 画板、共享绘画工具和本地图库。

### 验收

- `get_board` / `show_board` 在结构化内容里暴露 `capabilities`、`visualDigest` 和图库索引；纯文本宿主也能走同一套流程。
- `draw_board` 接受可选 `variant` / `style` / `z` / `role` / `startItemId` / `endItemId`，全部向后兼容并经过校验。
- 连接箭头按对象边界解析，人或 AI 移动端点后仍然成立；断链时安全降级而不是画错。
- 确定性布局支持 `grid` / `row` / `column` / `timeline` / `cluster`，不引入新工具或新依赖。
- 画布能渲染变体、样式、z 序、连接箭头和选择框，同时不把工具栏塞满。
- 图库保存/切换仍只有一张活动画板，上下文同步与 `get_board` 跟随新快照。
- `npm run check` 通过，本地预览服务新模板，HTTP 与 MCP 两条路径都能切换已保存的画板。

### 视觉配方

这些是**使用图元的建议**，不是模板库、不是 Mermaid 渲染器、也不是新的对象模型：

- **流程**：一排带标签的矩形或便签，`line` 配 `startItemId` / `endItemId`，边标签要短，布局用 `timeline` 或 `grid`。
- **对比**：两到三个 `role: "column"` 框架，子项标签对齐，每列一个 `groupId`，不要用假连线文字。
- **聚类**：`groupId` 配 `layout.mode: "cluster"`，加一个短 `title` 或 `role: "label"`。
- **强调**：给一个对象 `emphasis: "focus"`，用 `stroke` 圈出来，再加一句短说明。
- **图片批注**：有界的 `image` + 邻近的 `text` / `note` + 指向性箭头或笔迹，不要用文字覆盖图片。

## 4. Excalidraw 画布引擎

### 目标

用 `@excalidraw/excalidraw` 作为人类面向的无限画布，同时保住当时的四个 MCP 工具、version 1 `BOARD_JSON`、本地图库、终态上下文同步，以及标准页 / MCP App 双通道。当前工具面以目标 10 为准。

```text
BoardStore / MCP 工具 / HTTP API / BoardLibrary
  → 权威 version 1 board.json
  → Doodle ↔ Excalidraw 适配层
  → Excalidraw React 画布
  → onChange 投影回 Board v1
  → get_board / 模型上下文 / 图库快照
```

### 验收

- Excalidraw、React、ReactDOM 版本固定，本地用 esbuild 打包，不存在 CDN 引用。
- 生产 CSS 与字体复制进 `dist/infra/templates/excalidraw/` 和插件包，`GET /` 直接提供 Excalidraw 画布，没有 DOM 引擎兜底。
- Board v1 对象投影为 Excalidraw 元素时 ID 稳定，并带 `customData.doodle`；人的编辑能反向投影回 Board v1，矩形、椭圆、菱形、文本、箭头、线、手绘、图片、框架、分组都有确定性映射。
- `draw_board`、HTTP 批量/替换、图库切换都会刷新 scene，但不破坏版本安全。
- MCP App 上下文同步与「通知 Agent」在 Excalidraw 引擎下依然可用。
- 语义图生成留在 Board v1 内，只有一个确定性布局解析器，没有独立的 scene 端点。
- `npm run check` 通过，本地预览经肉眼验证。

### 已知成本

去掉重复的 Excalidraw 生产 JS/locales 后，`npm pack --dry-run` 约为 16.0 MB 压缩 / 22.9 MB 解压、约 512 个文件。重量主要来自自托管字体、locales 和按需加载的 Mermaid chunk。这是"不使用 CDN、不依赖外部字体、不要 license key"的代价，`0.8.0` 选择如实记录，而不是宣称包很小。

### 稳定化修复（记录在案的踩坑）

- 形状内文字曾是两个 Board 对象，渲染时叠加；现在是一个对象 + 一个 Excalidraw 绑定文本元素。
- `onChange(elements, appState, files)` 必须保留图片文件数据，并在文本/线条/分组编辑期间暂停持久化。
- 场景保真度放在可选的 `scene` 元数据里；没有 `scene` 的老画板依然合法。
- 标准页监听 WebSocket 的 `board_updated` / `board_library_updated`，但只在人没有正在编辑时才刷新。
- 曾经的"原生 scene"实验被移除，避免画板与场景两份状态分叉。

## 5. Codex 插件分发

### 目标

保持**一张简单的共享无限画板**，同时把它打包成可一键安装的本地 Codex 插件。插件包裹同一个 MCP stdio 服务；MCP Apps 渲染仍然只是可选的宿主增强，不是第二个产品，也不是纯文本宿主的硬性要求。

```text
一键安装 → 新会话 → 首句提示 → 插件清单 → 内置 stdio MCP 服务 → 三个绘画工具 → 一张本地画布
```

### 边界

插件是**分发层**。它不能把 Doodle 变成托管服务、聊天产品、审批流程、项目看板、代码变更授权，也不能变成工具集不同的另一个 MCP 服务。

### 验收

- 插件清单使用 `.codex-plugin/plugin.json` + `.mcp.json`，入口指向 `${PLUGIN_ROOT}/server/index.mjs`；仓库内 marketplace 指向生成的 `.doodle-plugin/doodle`。
- `npm run setup:codex` 一条命令完成：按需装依赖、构建插件、注册本地 marketplace、安装 `doodle@doodle`、打印首句提示；重复执行安全，`--dry-run` 只预览命令。
- 全新检出可一条命令安装，不依赖手写绝对路径；直接 MCP 配置是零配置片段。
- 两条路径都只暴露 `get_board`、`show_board`、`draw_board` 三个绘画工具。
- `get_board` 返回渐进式引导、`BOARD_JSON` 和活动的 loopback `PANEL_URL`，且**不打开浏览器**。
- 插件使用隔离的可写状态目录和空闲 loopback 端口；`OUTPUT_DIR` / `PREVIEW_PORT` 仍可显式覆盖。
- `show_board` 仍是显式渲染工具；成功的 `draw_board` 也会附带画布资源，让兼容宿主自动显示。纯文本宿主全程可用。
- `npm run check` 通过，CI 跑同一套插件守卫与 setup dry-run，并构建带版本号的提交 ZIP。
- `git status` 只有预期的已跟踪改动，没有生成的运行时、提交 ZIP 或私有画板状态。

### 不在范围

公共插件目录提交、伙伴白名单、组织认证、门户审核；托管账号、多用户、OAuth、公网端点、远程状态、遥测；新的画板协议或第五个工具；npm 发布与仓库元数据修改。

## 6. 画板上下文经济

### 目标

让**重复读同一张画板变得又便宜又稳定**，同时不削弱人类画布、当时的四工具契约和 version 1 兼容性。

```text
首次读  → 足够画出正确结果的结构
再次读  → 紧凑增量 + 稳定摘要，而不是整个场景
人类画布 → 本地保留完整场景保真度
```

### 为什么值得做

产品主张是"画板是人机共享的语言"。但 AI 每次读取都要为这门语言付 token。实测一张 4 对象画板：`get_board` 整体 6,356 字符，其中持久化的 4,008 字节里有 **3,872 字节（97%）是每个 item 上的 Excalidraw `scene` 保真元数据**——AI 用不上、验不了、也不该改。这在一个"整天都用"的工具里是错的交易：画板越常用，读起来应该越便宜。

### 验收

- 同一张未变画板的重复读取，payload 有可测量的下降，并记录在本文件。
- `scene` 元数据绝不出现在默认的 agent payload 里，但有测试证明它仍被持久化、仍会送达到画布。
- 变更后的重读只返回变化对象和稳定摘要，而不是整张画板。
- 文档、守卫和插件 skill 描述同一套契约；`npm run check` 通过。

### 实测结果

同一张 4 对象画板，stdio MCP 客户端 + 真实工具返回：

| 读取 | 字符数 | 说明 |
|---|---|---|
| 本次迭代前 | 6,356 | 整张画板，含 `scene`，每次都带引导 |
| 迭代后首次读 | 8,237 | 引导只发一次，所以这一次带着它 |
| 第二次读（无参数） | 6,171 | 已省略引导 |
| 带 `since_revision` 重读 | 618 | 只返回增量，画板未变 |

- agent 投影比持久化画板小 **56%**（4,008 → 1,747 字节），`scene` 占持久化 payload 的 **65%**。
- 未变画板的重读比整读小 **90%**；变化后的重读只返回变化对象。
- `canvasFidelityItems` 报告有多少 item 被扣留了保真数据。

### 同一轮还交付了三件事

- **`diagram.mode` 表达的不再只有依赖图**：`flow`（默认，按边分层）、`timeline`、`compare`、`matrix`。只有 `flow` 读边来决定位置；显式 `row` / `column` 永远优先，作者写的顺序不会被悄悄打乱。
- **`HANDOFF` 告诉 AI 人改了什么**：只报告人类来源的变更（item 现在是 `human`，或人类 item 消失），AI 永不被要求复审自己上一次写入。每条最多 12 条改动，`omitted` 计数其余；没有人类改动时给一行明确说明，而不是沉默。
- **已移除的历史功能**：早期版本曾提供 `scan_project` 和 `DIAGRAM_DRAFT_JSON`；项目读取能力已于 2026-11-27 从 Doodle 中移除。

## 7. 纸面与玻璃外观

### 目标

提供三种可选外观——**浅色** / **深色** / **液态玻璃**——由一个三向切换器控制。浅色与深色是同一张纸在两种亮度下，玻璃是原始折射镜片。切换外观只改 chrome 和页面，**永不改画板内容**。

### 为什么默认是纸

画布是思考和随手画的地方，不是玻璃控制面板。纸读起来就是"可以往上写"的表面：温暖的未涂布纸、石墨墨色、安静的铅笔蓝点缀、可见的卡片边缘。深色是同一材料在关灯后——炭色纸 + 浅色墨，而不是绿色玻璃。

### 方向

1. **三种外观，一套机制**：`THEMES` 是唯一事实源，id 为 `light` / `dark` / `glass`；类型、持久化校验、切换器都从它派生。加第四种外观 = 一条 `THEMES` 记录 + 一个 token 块，不是一个新 `if (theme === …)`。
2. **配色与材料分离**：`data-doodle-theme` 选配色，`data-doodle-material` 选构建（浅深为 `paper`，玻璃为 `glass`）。所有材料规则挂在 `data-doodle-material` 上。
3. **纸是不透明卡纸，不是染色玻璃**：`--glass-lens-scale` / `--glass-lens-blur` / `--glass-frost` 全为 0 时，`liquid-glass.ts` 直接跳过滤镜生成。
4. **材质是被照出来的，不是叠上去的**：`--paper-relief` 把低频纸浆云斑与中频纸齿合成为一个高度场，再用 `feDiffuseLighting` 按左上单一光源打光后相乘进纸面。单纯叠加噪声只会压暗像素、没有法线，纸面仍然是平的；高度场让每个凹陷都有向光面与背光面。浅色纸把光照压在窄带内，深色纸必须用更宽的色调范围——炭色上方没有余量，对比只能来自更深的凹处，用 screen 会整片发灰。
5. **字必须可读**：界面是中文，纸面用 UI 字体、标题略大，不为"手写感"去拉几百个 `unicode-range` 分片。
6. **画板颜色是字面的**：Excalidraw 固定浅色主题，切外观不改人物体颜色，也不写画板状态。

### 验收

- 三种外观可切换、刷新后保持、首屏绘制前就生效（不闪另一个配色）。
- 浅色与深色使用 `data-doodle-material="paper"` 且不生成玻璃滤镜；玻璃保留透光。
- 默认 Excalidraw token 块等于浅色纸配色，玻璃与深色是显式覆写。
- 切换外观通过 `doodle-theme-change` 重算墨色，三种 id 都覆盖，且**零次画板写入**。
- 切换器可键盘到达，用 `aria-*` 暴露当前外观，420px 宽不溢出。
- 三种外观下正文与图标对其所在表面至少 4.5:1 对比度。
- `npm run check` 通过，含三种 id、材料分离、以及"Excalidraw token 里不得出现上游紫色"的守卫。

## 8. 一个会去用的画板

### 问题

不是"画板还能做什么"，而是：**为什么有人会打开 Doodle，而不是一张便利贴、一张餐巾纸、或干脆让 AI 用文字回？**

功能层面它已经完整：三个绘画工具、图库、图形作者能力、导出、三种外观、可用的 MCP App。但它还**不顺手**。要配置才能用的画板，不会成为你身边那张纸。

当时的摩擦有七步：

```text
clone → npm install → npm run build → 起预览或 MCP 宿主
→ 从终端输出里找端口 → 复制 URL → 打开浏览器
```

而最短路径干脆没有入口：`npx -y doodle-mcp` 只打印三行日志，不告诉人"画布在哪、接下来做什么"。

### 目标

一条动作就能到达画板，并且第一眼就看得懂，同时不把 Doodle 变成另一个产品。

```text
一条命令 → 画布打开、已聚焦、可直接画
无需配置 → 不用 agent 也能画，agent 不用人也能画
可恢复   → 上次用的那张画板，回来还是它
```

### 验收

- 干净检出下，一条有文档的命令把画板打开在默认浏览器里；打不开浏览器时改印可用 URL 而不是报错。
- 首次使用的人不查文档就能新建便签、画形状、平移、缩放；首屏说明这些手势且可永久关闭。
- 没有 MCP 宿主时也能独立画，画完后 agent 读到的就是同一张画板。
- 重新打开恢复活动画板，不重置图库。
- 加载、刷新、agent 会话丢失都不会删除对象。
- `npm run check` 通过，文档与守卫一致，每项改动都在真实画布上验证过，而不只是单测。

### 进展

**2026-11-15 — 一条命令打开 + 首访引导**

- `npm run doodle` 启动画板并打开默认浏览器；无浏览器时打印 URL 和同样的短提示（`--print` 可强制走这条路）。
- 直接跑服务也会在 `stderr` 打印两行人话提示和画板地址，与 `stdout` 的 JSON-RPC 分开。
- 空画板首次访问显示可关闭的引导卡：双击建便签、拖拽画形状、空格/滚轮平移、修饰键+滚轮缩放。关闭状态记在 localStorage，有内容的画板不再出现。

**2026-11-15 — 恢复、状态安全、手势审计**

- **恢复**：每张画板各自记住相机（滚动与缩放），上限 8 张。两条保护：空画板不恢复相机；记住的相机离内容太远则丢弃，避免满画板看起来是空的。
- **状态安全**：会把非空画板清空的写入改为 409 拒绝——"画板突然变空"几乎总是客户端 bug（当时就是画布在挂载前写了一个空场景）。按 id 主动删除不受影响，新画板首次写入也不受影响。
- **手势审计**：在真实画布里检查四条高频路径（建便签、拖形状、拖箭头、手绘），发现的唯一缺陷就是恢复相机把人留在空处，已修复。

**2026-11-15 — agent 读意图，而不是读 diff（历史工具面）**

当时，字段级增量回答"什么变了"，但回答不了"人想干什么"，agent 只好猜。`HANDOFF` 增加 `HANDOFF_READINGS`：每条人类改动一行，归类为改标签、移动、缩放、改样式、新增、删除，各带一条有界建议；`NEXT` 以最显著的那条开头。该工具面记录为版本历史；当前 Doodle 只提供三项绘画工具。

端到端验证：把便签从「开始」改成「从需求评审开始」，输出 `把「开始」改成了「从需求评审开始」，这是含义上的修正`，并建议同步周边标签。

**2026-11-24 — 首用引导不再挡住第一笔**

真实浏览器复现了两个叠加的首次体验缺陷：快捷键面板的自动打开条件写反，让 560px 面板压在 520px 欢迎卡上、之后再也不出现；欢迎卡只在点击「开始画」时隐藏，人直接画或 AI 先画第一个对象时，卡片会一直盖住刚画出的内容。现在两张浮层按「空板欢迎卡 → 关卡后下次弹一次快捷键 → 之后安静」的顺序交接，任意一方画出第一个对象都会让卡片退场并记住已读。

证据：独立空板的浏览器契约覆盖完整交接序列、人画穿卡片与 AI 先画两条路径；真实 MCP 会话走完 AI 画 → 人改 → AI 读 HANDOFF 的回路；`npm run check` 与 Node 20 最低版本 smoke 均通过。后续 0.9.1/0.9.2 补丁继续修复发布链和主题状态写回；0.9.2 已发布到 npm 与 GitHub Release，当时的干净 `npx -y doodle-mcp` 启动验证了四工具、`FIRST_USE` 与 `PANEL_URL`。当前产品边界见目标 10。

## 9. 让每次被拒绝的写入都可修复

### 目标

Doodle 的价值在于 AI 不用人纠语法就能在画板上表达意图。**每一次被拒绝、而模型又无法从返回里自行修好的调用，都是一次由人买单的往返。** 这个目标是：首次写入就成功；失败时错误本身能教模型怎么改。

```json
{ "code": "...", "message": "...", "path": "items[2].w", "expected": "...", "fix": "..." }
```

### 起始证据

把 server 当作什么都不懂的新模型来驱动，暴露了两类不同的失败：

1. **schema 层的拒绝完全绕过 `ERROR_JSON`。** 违反 Zod schema 的调用——文本超 1200 字符、超过 100 个 item、未知 `author`——返回裸 `MCP error -32602: Input validation error`，没有 code、没有路径、没有修法。而 `AGENTS.md` 承诺每个被拒绝的写入都带 `ERROR_JSON`，契约与实际行为在新模型最先撞上的那条路径上正好不一致。
2. **多数领域拒绝是散文。** 79 处 `throw new Error(...)` 对 8 处 `BoardValidationError`。"Stroke needs bounded points" 说了问题，但没说哪个字段、怎么改。

### 验收

- 每次被拒绝的写入都返回可机器修复的结构：`code` / `message` / `path` / `expected` / `fix`。
- 一套 first-try 套件对每种真实会发生的错误断言：返回里点明了字段，也给出了修法，并且**按 `fix` 改完确实能成功**。
- 边界值（长度、数量、坐标、尺寸、枚举）必须在 `model/` 里判，并带 `ERROR_JSON`；不能留在 schema 层。
- 守卫在出现"新的 schema 级拒绝却没有修复路径"时让 CI 失败。

**一个例外是契约的一部分，不是缺口**：**JSON 类型本身错**（`text: 42`、`x: "abc"`）由 MCP SDK 在任何 handler 之前拒绝，无法再序列化，返回的是 SDK 消息——而它已经点明了字段与期望类型（`expected string, received number at items[0].text`）。这在不看源码的前提下就是可修复的，所以保持原样，不去在 model 层复制整套 schema。**边界值不同**：它事先可知，所以必须在 `model/` 里，且必带 `ERROR_JSON`。

### 计划

1. schema 层的拒绝也走与领域拒绝相同的契约。
2. 按命中频率把写入路径里的裸 throw 改成 `BoardValidationError`：先 item 字段，再 stroke points、连接绑定、diagram 输入。
3. 画图引导文本直接告诉模型它会被哪些边界检查。
4. 用 first-try 套件冻结契约，守卫兜住回退。

### 交付结果

17 项修复，分四类：

- **错误契约（MCP）**：边界从 Zod 搬进 `model/`，schema 只描述形状；79 处裸 throw 结构化；`replace_board` 不再接受 `color: "nope"`；整板拒绝带 `items[N].<field>`；`title` / `groupId` 超长改为拒绝并报实际长度；`BOARD_ITEM_LIMIT`、`DIAGRAM_EMPTY`、`SCAN_RANGE_OUT_OF_RANGE`、`INVALID_SINCE_REVISION`、`INVALID_VIEW`、`BOARD_NOT_FOUND`、`UNKNOWN_LIBRARY_ACTION` 都带数量、上限与出路。
- **错误契约（HTTP，人侧画布）**：校验错误曾被误判成 errno 返回 **500**，现在先判类型再返回 400 + 完整结构；library 路由原本**没有任何错误处理**、全返回 500，现在与写入路径对齐为 400/409/503/500。
- **正确性**：无 `expected_revision` 的并发写入不再互相失败（`store.mutate` 锁内重读，两个都落地）；批量 `updates` / `remove_ids` 含未知 id 从"静默跳过却报成功"改为整批原子拒绝；`layout` 未知 id 不再排列整张板；切板后差量不再报"全增全删"；`replace_board` / `library` 与 `items` 同传不再静默丢弃。
- **成本与可发现性**：48 步流程图从 14,740px 高降到 938px；`show_board` 不再每次重发 guide（7.8 KB → 4.3 KB）；超过 80 对象时主动报告更便宜的读法。

**实测**：20 个真实会发生的错误，带字段路径 + 修复建议的从 **10 → 19**；剩下 1 个是 JSON 类型错，由 SDK 拦截且消息本身可修。测试 239 个，守卫 232 条（本轮新增 20 条）。

### 不在范围

不加新工具、不改画板状态、不改 UI、不改任何**合法**输入的结果。这个目标只改变"被拒绝的写入如何被报告"。

## 如何写一份新的目标文档

往本文件追加一节，保持同样的形状：

| 字段 | 含义 |
|---|---|
| 目标 | 一个具体的产品结果或维护结果 |
| 时间边界 | 带时区的起止时间，或明确的停止条件 |
| 权限 | 允许的提交、推送、文档、依赖与验证命令 |
| 红线 | 绝不执行的操作（通用红线已在上面，只写本目标特有的） |
| 证据 | 测试、构建、截图、CI 结果与最终审计产物 |

模板：

```text
在 <起> 到 <止>（<时区>）之间维护 <仓库>：围绕「<一个可测量的结果>」持续迭代。
允许正常提交并推送到 <分支>，更新文档、测试、CI 与离线守卫；每次增量运行 npm run check。
禁止 force push、改写历史、移动 tag、提交凭据或 output/dist、自动发布，以及绕过人工审阅的项目写入。
结束时列出提交、验证证据、已知限制与下一步。
```

宣布完成前，检查 `git status`、最近的提交、完整 diff、测试输出、package dry-run、本地 MCP 工具列表，确认没有禁止的产物被跟踪。宁可几个小而一致的提交，也不要一个看不出所以然的清理提交。

> `0.3.x` 时代的目标运行与工作台时期的证据属于归档记录（[archive/adr-legacy/](archive/adr-legacy/)），不代表当前产品行为。
