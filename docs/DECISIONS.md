# Current Decisions

`0.7.0` continues the simple shared infinite board and installable desktop-only Codex plugin from `0.6.0`, with the complete install-to-use path optimized. The product is explicitly two-way: people and AI both draw on the board to express intent and read each other's visual context. The plugin wraps the same four-tool MCP stdio server; direct MCP configuration remains supported. MCP Apps rendering is an optional host enhancement; capable hosts receive final-state board context in the current host conversation and can send one short user notification from the canvas. A standalone local page remains available. Discussion stays in the host conversation; Doodle owns only shared visual context.

## Decisions in force

0. **The product is called Doodle.** The project and GitHub repository are `Doodle`; the npm package, CLI, and MCP server identity are `doodle-mcp`.
1. **The board is the product.** `BOARD_JSON` is the only shared collaboration state. It is independent of project files, graph sessions, and proposal state.
1a. **The product story is one kernel, two entry points, three capability layers.** One shared board; Codex plugin or direct MCP; four tools everywhere, optional embedded canvas, optional context sync and notification. Project structure is optional source material, not a product pillar.
2. **The agent chat stays in the host.** Remove the duplicate composer and message feed from Doodle. The MCP App remains optional and calls existing board tools through the host bridge; text-only MCP clients retain their complete workflow.
3. **Four MCP tools are enough.** `get_board` reads progressive guidance, canvas data, and `PANEL_URL`, `show_board` renders the optional UI, and `draw_board` mutates objects. `scan_project` is an optional read-only project-structure helper. The chat-like `reply_on_board` tool remains removed.
4. **AI development stays inside the agent.** No tool opens a browser, IDE window, or editor. Logs stay on stderr; stdout remains clean for MCP JSON-RPC.
5. **Project scanning is context, not authority.** `scan_project` returns bounded relative paths and `file:line` evidence text. It does not draw automatically, write files, or grant code-change authority.
6. **Directed arrows are a canvas primitive.** A `line` goes from `(x,y)` to `(x+w,y+h)`; signed `w`/`h` are endpoint deltas and `shape` may be `straight`, `curve`, or `orthogonal`. Both views render the same SVG arrow contract.
6a. **The board grows through optional version 1 fields.** Freehand `stroke`, local `image`, `title`, `groupId`, and `emphasis: focus` extend visual expression without a schema version bump or migration; older boards remain valid.
7. **Human writes are explicitly local.** Non-GET `/api/board/*` requests require `X-AI-Draw-Token` and `confirmedBy: "human"`. The server binds to `127.0.0.1` by default.
8. **No project-write protocol is bundled.** Code changes remain ordinary coding-agent work. Board objects never become approval credentials or automatic file edits.
9. **Dependencies follow the product.** Mermaid rendering, image conversion, IDE launchers, nanoid, and VS Code extension code were removed in `0.4.0`; MCP Apps and esbuild support the optional embedded canvas from `0.5.0`. The `0.6.0` plugin reuses the same dependencies through one bundled server.
10. **Board mutations are serialized across processes.** Every mutation acquires a filesystem lock, reads the latest board, and atomically replaces it through a unique temporary file. Browser snapshot writes require an exact expected revision and reject stale writes.
11. **Project evidence is secret-filtered and bounded.** Scans omit lines that resemble common credential names or formats and return at most 40 evidence lines in total.
12. **Canvas gestures stay direct and reversible.** Click places a default-sized object; drag sizes shapes, draws arrows, or sketches. The pen emits ink immediately on pointer-down and stays active for continuous strokes; the eraser removes only touched freehand ink segments in one undoable batch and leaves other object types untouched. Double-click empty canvas creates a note; marquee multi-select enables batch move/delete/group/layout. Undo/redo, arrow-key nudging, alignment snapping, and bounded image paste are human-local conveniences. Space/middle drag pans, the wheel pans, and Ctrl/Command-wheel zooms. Escape cancels the current gesture or text edit.
13. **The plugin is a distribution layer, not a second product.** One Codex-compatible manifest, one `.mcp.json`, a repository marketplace, one skill, and one self-contained server bundle expose the same four tools and version 1 board state. Portable Agent Plugins manifests are not mixed into the package.
14. **Plugin runtime is local and robust.** MCP stdio connects before the optional HTTP preview; preview failure does not disable tools. Without `PREVIEW_PORT`, or with `PREVIEW_PORT=0`, the server binds a free loopback port and `get_board` reports `PANEL_URL`. `OUTPUT_DIR`, plugin data, or workspace-local `.doodle-data` isolate board state, while `DOODLE_WORKSPACE_ROOT` still scopes `scan_project`.
15. **The plugin build is reproducible.** `scripts/build-plugin.mjs` copies both canvas templates and the MCP App bundle, injects the package version, and writes ignored `.doodle-plugin/` output. `npm run check` and CI run the plugin guard.
16. **Public submission materials are separable from approval.** The repository prepares explicit tool annotations, privacy/support/terms URLs, a versioned ZIP, and `docs/SUBMISSION.md`; allowlisting, verified identity, portal attestations, clean desktop testing, and approval remain OpenAI-side conditions.
17. **Install and first use are one path.** `npm run setup:codex` is the only recommended Codex install command; `npm run check` never changes global Codex configuration. Direct MCP snippets are zero-configuration `npx -y doodle-mcp`. The first prompt, visible canvas, two-way drawing, final-state sync, and AI reread are documented together. The four-tool protocol and version 1 board state are unchanged.
18. **Product guidance is progressive, not hidden.** An empty `get_board` leads with one `FIRST_USE` and one `NEXT_STEPS` line plus the drawing guide; later reads use one short `NEXT` block and omit repeated guidance. MCP initialization instructions retain the full contract. The canvas has one dismissible `?` popover that opens only on demand; contextual edit/delete actions appear only for a valid selection, and view/help preferences stay in the browser only.
19. **New boards start empty.** A clean server writes a version 1 empty board with one initial revision. The retained `createStarterBoard` function remains only for compatibility and tests; the first visual object should come from a person or the AI's first prompt.
20. **Visual edits record their current author.** Human HTTP writes set `author: "human"`; AI `draw_board` updates set the top-level author, defaulting to `ai`. This prevents the canvas badge and `copyText` from contradicting the last edit.
21. **Live experience is audited.** [`EXPERIENCE_AUDIT.md`](EXPERIENCE_AUDIT.md) records the end-to-end AI/human test, priorities, acceptance, and closure. Product changes update it rather than adding a parallel roadmap.
22. **Distribution status is explicit.** A GitHub Release and source plugin install do not imply that `npx -y doodle-mcp` serves the same version. Maintainers verify `npm view doodle-mcp@<version> version` and one `npx` startup after the 2FA-gated approval; `EXPERIENCE_AUDIT.md` records the current publication state. For `0.6.3`, both the plugin checkout path and npm direct-MCP path resolve to the same version.
23. **Host context sync is final state, not history.** In MCP Apps hosts that advertise `updateModelContext`, the embedded board publishes the complete current board snapshot plus `added` / `updated` / `removed` differences from its last successfully published snapshot. Differences contain final object values or removed IDs, never click, drag, text-input, or tool-call operations. Each update overwrites prior context and does not trigger a model turn. `get_board` remains authoritative.
24. **Notification stays in the host chat.** When `sendMessage` is also supported, one `通知 Agent` button sends exactly a short message such as `我改了 Doodle 画板，你看下图。` into the existing host conversation. Automatic sync never calls `sendMessage`; Doodle gains no chat pane, second session model, message feed, or automatic model response. Standalone `PANEL_URL` and hosts without both capabilities hide the button and use `get_board` rereading.
25. **Saved images are editable boards, not static exports.** A local library stores named version 1 snapshots under `OUTPUT_DIR/.doodle/boards/`. `draw_board.library` and the human `图库` panel share one action vocabulary for save/switch/create/rename/duplicate/delete/import/export. Switching replaces the single active board state; `get_board`, MCP App context, and the standalone canvas all follow that active board. No PNG/SVG exporter, diagram asset catalogue, or second collaboration model is introduced.
26. **Visual meaning comes from bounded composition, not a template engine.** `get_board`, `show_board`, and HTTP `GET /api/board` expose deterministic `capabilities`, `visualDigest`, and recipes. Optional version 1 fields add variants, roles, z-order, bounded styles, group identity, and connector bindings. Connected lines resolve to bound object edges. Five deterministic layout modes cover flow, compare, cluster, and ordinary arrangement without a dependency, static diagram library, or fifth MCP tool.
25. **Context is bounded but authoritative in structured form.** The text projection trims long labels and may omit old objects from its readable list; `structuredContent` carries the full current version 1 snapshot, the final-state delta, and fixed read-only flags. Capability failures are logged in the embedded app without interrupting canvas editing or falsely reporting synchronization.

## MCP App boundary

Official OpenAI documentation describes custom MCP UI as optional, recommends separating data tools from render tools, confirms the `.codex-plugin/plugin.json` compatibility layout, and marks local stdio MCP plugins desktop-only. Local marketplaces are separate from the universal public directory; installed plugin skills and MCP tools are used in a new session. Doodle attaches its canvas to `show_board` and to successful `draw_board` results so a completed AI drawing is visible immediately in compatible hosts; its UI refreshes through `get_board`. The MCP Apps SDK describes `updateModelContext` as a deferred, overwrite-only model context update and `sendMessage` as a conversation message that can trigger a follow-up; Doodle keeps those roles separate. Text-only hosts and plugin installs use the same tools and should call `show_board` after drawing when supported. See [Add UI to your MCP server](https://developers.openai.com/plugins/build/chatgpt-ui), [Package your plugin](https://developers.openai.com/plugins/build/plugins), [Developer commands](https://learn.chatgpt.com/docs/developer-commands), and [Submit desktop-only plugins](https://developers.openai.com/plugins/deploy/desktop-only).
