# Current Decisions

`0.8.0` continues the simple shared infinite board and installable desktop-only Codex plugin from `0.6.0`, with the complete install-to-use path optimized. The product is explicitly two-way: people and AI both draw on the board to express intent and read each other's visual context. The plugin wraps the same four-tool MCP stdio server; direct MCP configuration remains supported. MCP Apps rendering is an optional host enhancement; capable hosts receive final-state board context in the current host conversation and can send one short user notification from the canvas. A standalone local page remains available. Discussion stays in the host conversation; Doodle owns only shared visual context.

## Decisions in force

0. **The product is called Doodle.** The project and GitHub repository are `Doodle`; the npm package, CLI, and MCP server identity are `doodle-mcp`.
1. **The board is the product.** `BOARD_JSON` is the only shared collaboration state. It is independent of project files, graph sessions, and proposal state.
1a. **The product story is one kernel, two entry points, three capability layers.** One shared board; Codex plugin or direct MCP; four tools everywhere, optional embedded canvas, optional context sync and notification. Project structure is optional source material, not a product pillar.
2. **The agent chat stays in the host.** Remove the duplicate composer and message feed from Doodle. The MCP App remains optional and calls existing board tools through the host bridge; text-only MCP clients retain their complete workflow.
3. **Four MCP tools are enough.** `get_board` reads progressive guidance, canvas data, and `PANEL_URL`, `show_board` renders the optional UI, and `draw_board` mutates objects. `scan_project` is an optional read-only project-structure helper. The chat-like `reply_on_board` tool remains removed.
4. **AI development stays inside the agent.** No tool opens a browser, IDE window, or editor. Logs stay on stderr; stdout remains clean for MCP JSON-RPC.
5. **Project scanning is context, not authority.** `scan_project` returns bounded relative paths and `file:line` evidence text. It does not draw automatically, write files, or grant code-change authority.
6. **Directed arrows are a canvas primitive.** A `line` goes from `(x,y)` to `(x+w,y+h)`; signed `w`/`h` are endpoint deltas and `shape` may be `straight`, `curve`, or `orthogonal`. Both views render the same SVG arrow contract.
6a. **The board grows through optional version 1 fields.** Freehand `stroke`, local `image`, `title`, `groupId`, and `emphasis: focus` extend visual expression without a schema version bump or migration; older boards remain valid.
7. **Human writes are explicitly local.** Non-GET `/api/board/*` requests require `X-AI-Draw-Token` and `confirmedBy: "human"`. The server binds to `127.0.0.1` by default.
8. **No project-write protocol is bundled.** Code changes remain ordinary coding-agent work. Board objects never become approval credentials or automatic file edits.
9. **Dependencies follow the product.** Mermaid rendering, image conversion, IDE launchers, nanoid, and VS Code extension code were removed in `0.4.0`; MCP Apps and esbuild support the optional embedded canvas from `0.5.0`. The `0.6.0` plugin reuses the same dependencies through one bundled server.
10. **Board mutations are serialized across processes.** Every mutation acquires a filesystem lock, reads the latest board, and atomically replaces it through a unique temporary file. Browser snapshot writes require an exact expected revision and reject stale writes.
11. **Project evidence is secret-filtered and bounded.** Scans omit lines that resemble common credential names or formats and return at most 40 evidence lines in total.
12. **Canvas gestures stay direct and reversible.** Click places a default-sized object; drag sizes shapes, draws arrows, or sketches. The pen emits ink immediately on pointer-down and stays active for continuous strokes; the eraser removes only touched freehand ink segments in one undoable batch and leaves other object types untouched. Double-click empty canvas creates a note; marquee multi-select enables batch move/delete/group/layout. Undo/redo, arrow-key nudging, alignment snapping, and bounded image paste are human-local conveniences. Space/middle drag pans, the wheel pans, and Ctrl/Command-wheel zooms. Escape cancels the current gesture or text edit.
13. **The plugin is a distribution layer, not a second product.** One Codex-compatible manifest, one `.mcp.json`, a repository marketplace, one skill, and one self-contained server bundle expose the same four tools and version 1 board state. Portable Agent Plugins manifests are not mixed into the package.
14. **Plugin runtime is local and robust.** MCP stdio connects before the optional HTTP preview; preview failure does not disable tools. Without `PREVIEW_PORT`, or with `PREVIEW_PORT=0`, the server binds a free loopback port and `get_board` reports `PANEL_URL`. `OUTPUT_DIR`, plugin data, or workspace-local `.doodle-data` isolate board state, while `DOODLE_WORKSPACE_ROOT` still scopes `scan_project`.
15. **The plugin build is reproducible.** `scripts/build-plugin.mjs` copies both canvas templates and the MCP App bundle, injects the package version, and writes ignored `.doodle-plugin/` output. `npm run check` and CI run the plugin guard.
16. **Public submission materials are separable from approval.** The repository prepares explicit tool annotations, privacy/support/terms URLs, a versioned ZIP, and `docs/SUBMISSION.md`; allowlisting, verified identity, portal attestations, clean desktop testing, and approval remain OpenAI-side conditions.
17. **Install and first use are one path.** `npm run setup:codex` is the only recommended Codex install command; `npm run check` never changes global Codex configuration. Direct MCP snippets are zero-configuration `npx -y doodle-mcp`. The first prompt, visible canvas, two-way drawing, final-state sync, and AI reread are documented together. The four-tool protocol and version 1 board state are unchanged.
18. **Product guidance is progressive, not hidden.** An empty `get_board` leads with one `FIRST_USE` and one `NEXT_STEPS` line plus the drawing guide; later reads use one short `NEXT` block and omit repeated guidance. MCP initialization instructions retain the full contract. The canvas has one dismissible `?` popover that opens only on demand; contextual edit/delete actions appear only for a valid selection, and view/help preferences stay in the browser only.
19. **New boards start empty.** A clean server writes a version 1 empty board with one initial revision. The retained `createStarterBoard` function remains only for compatibility and tests; the first visual object should come from a person or the AI's first prompt.
20. **Visual edits record their current author.** Human HTTP writes set `author: "human"`; AI `draw_board` updates set the top-level author, defaulting to `ai`. This prevents the canvas badge and `copyText` from contradicting the last edit.
21. **Live experience is audited.** [`EXPERIENCE_AUDIT.md`](EXPERIENCE_AUDIT.md) records the end-to-end AI/human test, priorities, acceptance, and closure. Product changes update it rather than adding a parallel roadmap.
22. **Distribution status is explicit.** A GitHub Release and source plugin install do not imply that `npx -y doodle-mcp` serves the same version. Maintainers verify `npm view doodle-mcp@<version> version` and one `npx` startup after the 2FA-gated approval; `EXPERIENCE_AUDIT.md` records the current publication state. For `0.6.3`, both the plugin checkout path and npm direct-MCP path resolve to the same version.
23. **Host context sync is final state, not history.** In MCP Apps hosts that advertise `updateModelContext`, the embedded board publishes the complete current board snapshot plus `added` / `updated` / `removed` differences from its last successfully published snapshot. Differences contain final object values or removed IDs, never click, drag, text-input, or tool-call operations. Each update overwrites prior context and does not trigger a model turn. `get_board` remains authoritative.
24. **Notification stays in the host chat.** When `sendMessage` is also supported, one `通知 Agent` button sends exactly a short message such as `我改了 Doodle 画板，你看下图。` into the existing host conversation. Automatic sync never calls `sendMessage`; Doodle gains no chat pane, second session model, message feed, or automatic model response. Standalone `PANEL_URL` and hosts without both capabilities hide the button and use `get_board` rereading.
25. **Saved images are editable boards, not static exports.** A local library stores named version 1 snapshots under `OUTPUT_DIR/.doodle/boards/`. `draw_board.library` and the human `图库` panel share one action vocabulary for save/switch/create/rename/duplicate/delete/import/export. Switching replaces the single active board state; `get_board`, MCP App context, and the standalone canvas all follow that active board. Static PNG/JPG/SVG exports are sharing-only outputs; the library itself stores no image assets, diagram catalogue, or second collaboration model.
26. **Image export is a human-canvas capability, and the agent capability block must say so.** `library.export` returns editable version 1 JSON. The PNG/JPG/SVG sharing snapshots come from the canvas `图库 → 分享快照` buttons, driven by Excalidraw's `exportToBlob` / `exportToSvg` in the browser. There is deliberately no fifth MCP tool that returns an image file. `boardCapabilities()` therefore carries `libraryFormat`, `sharingExports`, `sharingExportOwner`, and `sharingExportHint`, because the bare `library: [..., "export"]` list read to a model as "JSON only, no image export" and produced exactly that wrong answer to a person. Guidance, MCP instructions, and the plugin skill repeat the distinction.
26. **Visual meaning comes from bounded composition, not a template engine.** `get_board`, `show_board`, and HTTP `GET /api/board` expose deterministic `capabilities`, `visualDigest`, and recipes. Optional version 1 fields add variants, roles, z-order, bounded styles, group identity, and connector bindings. Connected lines resolve to bound object edges. Deterministic layout modes, including `architecture`, cover ordinary arrangement and connected object sets without a dependency, static diagram library, or fifth MCP tool.
27. **Excalidraw is the shipped canvas engine, not the product model.** Since `0.8.0`, `@excalidraw/excalidraw` renders and edits the human canvas, but Doodle Board v1 remains the only persisted state and the only AI-facing board contract. Excalidraw elements are derived from Board v1 on every render; optional scene metadata preserves editing fidelity, but no separate scene file or render-time scene source is authoritative. The embedded canvas also keeps final-state context sync and the `通知 Agent` button. The removed DOM engine is history, not a fallback. Full acceptance and red lines are in `GOALS.md`.
28. **Semantic diagrams stay inside Board v1.** `draw_board.diagram` accepts bounded nodes/edges and adds one deterministic version 1 diagram beside existing objects; `replace: true` intentionally clears the active board: short labels, layered coordinates, bounded detail text, and bound arrows. It shares one layout resolver with the HTTP diagram endpoint, rejects duplicate node IDs and unknown edge endpoints, and cannot be combined with other mutation fields. This reduces AI coordinate errors without introducing a second persisted scene format.
29. **Context is bounded but authoritative in structured form.** The text projection trims long labels and may omit old objects from its readable list; `structuredContent` carries the full current version 1 snapshot, the final-state delta, and fixed read-only flags. Capability failures are logged in the embedded app without interrupting canvas editing or falsely reporting synchronization.
30. **Overlays never reflow the canvas, and hover feedback never changes geometry.** The `图库` drawer is an overlay above the canvas with a scrim, a fixed header and action area, and one independently scrolling named-board list. It does not add padding to the Excalidraw host, because that compression pushes Excalidraw's three-column top menu beyond the viewport and overlaps controls. Its launcher hides while the drawer is open so the same toggle does not sit above the panel. Hover and active states may change color, border, and shadow only; transforms, scaling, rotation, margins, padding, and size changes are rejected because they move neighbouring controls and cause transient overlap.
31. **Excalidraw owns its transient layers.** Doodle's top bar is positioned below Excalidraw's permanent toolbar, but both share the top-left region. Native dropdowns and modals are transient task surfaces, so the Doodle bar becomes non-interactive and visually hidden while `.excalidraw .dropdown-menu` or `.excalidraw .Modal` exists, then returns automatically. Doodle does not raise its z-index or leave an opaque launcher on top of the native menu, and it does not duplicate native menu actions.
32. **The human canvas does not navigate to third-party sites.** A custom Excalidraw main menu replaces the upstream social group with local search, local help, and exactly one GitHub link to `https://github.com/2648782102/Doodle`. The native help header, materials-library browse link, free web-embed tool, and AI/Mermaid generation entries are removed; `aiEnabled` is false. Canvas object links and `<a>` clicks are checked in both the capture listener and `onLinkOpen`, and anything other than this repository is prevented rather than opened. Internal popovers, dialogs, search, and the local board library remain unchanged. Documentation links in repository Markdown are not runtime surfaces and are not affected.
33. **One palette owns both the shell and the canvas.** Doodle's warm paper, pine-green accent, ink, muted, border, and shadow tokens are mirrored into Excalidraw's own CSS variables rather than applied as a filter. The light theme maps native islands to warm off-white, surfaces to muted sage-gray, and primary/selection/focus to pine green; the dark theme maps islands to green-tinted charcoal, surfaces to warmer raised green-gray, and primary to pale mint. This keeps native selected-tool, zoom, help, menu, dialog, and sidebar chrome visually inside Doodle instead of showing upstream violet. Guard checks reject `#6965db` and require both theme mappings.

34. **Agent context is a projection, not the board file.** The persisted board keeps Excalidraw `scene` fidelity for the human canvas, but agent payloads replace it with a `canvasFidelity` marker plus `canvasFidelityItems`. The agent cannot draw with `scene`, cannot verify it, and must not edit it; repeating it made real boards ~65% metadata. The persisted state and the canvas are unchanged, and a test asserts the withheld data is still written to disk. The canvas is the other consumer of the same tool: it rebuilds its scene from `structuredContent`, so `get_board` accepts `include_canvas_fidelity: true` and the canvas client always passes it. `src/board/agent-view.ts` owns the projection.

35. **Rereads are deltas with attribution.** `get_board.since_revision` returns only changed objects from a bounded in-memory revision cache, plus `HANDOFF`: human-attributed `added` / `edited` / `removed` entries with clipped final values. Only human changes are reported, because telling the agent to review its own last write is noise. A cache miss falls back to a full read and says so. This keeps the two-way loop cheap without adding a fifth tool, a second store, or an operation log.

36. **Diagram layout follows the kind of explanation.** `draw_board.diagram.mode` selects `flow` (edges derive columns), `timeline`, `compare`, or `matrix` (explicit `column` / `row`). Only `flow` reads edges for placement: a roadmap or a trade-off has an author-chosen order that edge analysis would silently break. Unplaced nodes fall back to declaration order rather than stacking at the origin.

37. **Opacity is one concept with two scales.** Board v1 stores opacity as a 0-1 fraction; Excalidraw stores 0-100. The adapter converts at the boundary (`boardOpacityToExcalidraw`) and back. Skipping that conversion is not a cosmetic rounding error: `1` becomes 1%, and a board with correct data renders as an empty canvas. This was a real shipped bug, fixed with a round-trip test.

38. **AI usability is a protocol property, not an extra tool.** The seven AI-experience improvements stay inside the four existing tools. `get_board` carries a bounded visual diagnosis and optional graded views; errors carry `ERROR_JSON` with a repair path; `diagram.recipe` expands short intent into the existing deterministic layout; `draw_board` returns `CHANGE_JSON`; capabilities document role semantics. Alternatives considered: adding a diagnosis tool, a recipe tool, and a change-log tool. Rejected because they would enlarge the tool surface and fragment the context the model needs in one read. The cost is a richer payload contract, locked by prompt-contract tests and the golden model snapshot.

39. **A write result is a canvas repaint, not a second read.** `draw_board` attaches its canvas to the result, so the embedded app repaints from the write instead of issuing a follow-up read. That made the full agent payload (`copyText`, `visualDigest`, `diagnosis`, `capabilities`, `safety`) ride along on every stroke: 13.5 KB returned for a single-note edit on a 26-object board, of which `applyRemoteSnapshot` consumed 6.7 KB. The write result is now `boardWriteSnapshot` — `id`, `title`, `revision`, `updatedAt`, `itemCount`, `items`, and `library`. `get_board` keeps the complete agent contract, so nothing is lost, only deferred to the read that actually wants it.

   `items` stays complete in that snapshot, timestamps included. The canvas keeps the write result as `activeSnapshot` and echoes it back as `replace_board` on the next human edit, so trimming fields here would silently drop them from the person's own path — the same class of bug as the earlier centred-caption drift. A repo guard fails if the write result reverts to `boardJson`.

   Library actions return the same shape. They previously returned the agent payload only, while the canvas looked for `result.board`; that key never existed, so save, switch, create, rename, duplicate, delete, import, and export each silently fell back to a fresh `/api/board` fetch. The flat snapshot now describes the *active* board — exporting a different saved board must not switch the person's view — and the requested board travels in `exportBoard` for the download.

40. **A graded view sends the board once.** The `BOARD_JSON` text copy is byte-identical to `structuredContent` — 11 KB of an 18 KB text block on a 25-object board — and it exists for hosts that only surface text. Every graded view was shipping both halves anyway, so `view: "detail"` cost 28.6 KB for 11 KB of payload; the level that promised fewer tokens was barely cheaper than `full`. Graded views now emit `BOARD_VIEW_<LEVEL>` plus a byte count and leave the data to `structuredContent`, which every MCP client receives. `full` keeps the complete text copy because that is its contract. Agent items also dropped per-item timestamps: `agentFingerprint` already excluded them, so they were 28% of the item payload with no reader.

41. **Bounds live in the model, not the input schema.** The MCP SDK validates `inputSchema` before a tool handler runs and converts a failure into `MCP error -32602`, which has no code, path, or fix. Keeping numeric and length bounds in Zod therefore produced two classes of rejection: a bad colour returned a full `ERROR_JSON` while a 1,300-character text or a 200-item batch returned prose, on exactly the paths a fresh model hits first. Schemas now describe shape only. `model/` already enforced every bound, so the repair path is identical regardless of which layer notices, and `model/limits.ts` stays the single source. `capabilities.limits` publishes the table so a model can size its first attempt correctly.

   A wrong JSON type (`text: 42`) is the deliberate exception: only the schema can catch it, its SDK message already names the field and expected type, and duplicating shape validation in `model/` would buy nothing. The distinction is *knowable up front* — a bound is, a mistyped field is not.

42. **An unpinned write is an append, so it belongs in the lock.** `draw_board` without `expected_revision` used to read the board outside the store lock and then call `replaceIfRevision` with that revision. Two agents drawing simultaneously produced `expected N, found N+1` for the loser: nothing was corrupted, but a legitimate write failed for a reason the caller could not act on. HTTP already used `store.mutate` for exactly this case, which is what made the MCP gap visible. Unpinned writes now re-read inside the lock. A pinned write keeps the strict check — `expected_revision` is a claim about what the caller last saw, and quietly rebasing it onto a newer board would overwrite whoever got there first.

43. **Library actions default to switching, and that default is a documented hazard.** `create`, `save`, `duplicate`, and `import` make the result active unless `switchTo: false`. The canvas depends on it — you just made a board, you want to see it — but an agent tidying the library would move the person's view out from under them. Rather than change the default and break the canvas, every field states its default and the `library` description tells the model to pass `switchTo: false` for housekeeping. Silent side effects are the problem; a documented default is a contract.

44. **A debounced canvas write is re-based, never dropped.** `onChange` waits 450 ms before writing. When a remote write landed inside that window, the timer callback returned silently: the person's drag stayed on screen, was never saved, and no banner said so — the worst possible failure, because the board still looked saved. A write is not invalid just because someone else got there first. The pending scene is now re-projected against the newest board at flush time, and the diff is computed there. The naive version of that fix resurrects objects: a scene that predates an agent deletion still contains them, so re-projecting turns the deletion into an addition and the object the person watched disappear comes back. `rebaseScene` therefore compares the scene's *provenance* board (`getSceneBase()`, not the newest one) with the latest and drops exactly the elements that disappeared. Locally created elements are never in the provenance board, so they always survive. When the rebase drops something, the canvas repaints from the write result — after the write, never mid-gesture. `test/sync-loop.test.mjs` covers both halves; `scripts/repo-check.mjs` fails if the silent `return` comes back.

45. **The canvas states its sync phase, and a conflict is a decision, not a toast.** "Did that save?" and "does the agent know?" had no answer in the UI: a rejected write was an eight-second toast, and host context sync was invisible. The canvas now shows one chip with a finite phase — `未保存` / `保存中` / `已保存` / `已同步` / `等 Agent`, plus `待处理` and `已断线` — and states which path it is on (`本机页面` or `宿主内嵌`). `已同步` is only claimed after `updateModelContext` actually resolves, because a capability that is present can still fail; there is deliberately no "agent read it" phase, since nothing in the protocol reports that. A conflict keeps its own surface: it names the objects that collided and offers exactly two exits, `载入最新` (take the server's version) and `保留我的` (re-send against the newest revision). Automatic overwrite in either direction is not offered, because both writers meant their edit. The phase machine is pure and tested in Node; the chip is markup in the template so it cannot exist on one entry path and be missing on the other.

## MCP App boundary

Official OpenAI documentation describes custom MCP UI as optional, recommends separating data tools from render tools, confirms the `.codex-plugin/plugin.json` compatibility layout, and marks local stdio MCP plugins desktop-only. Local marketplaces are separate from the universal public directory; installed plugin skills and MCP tools are used in a new session. Doodle attaches its canvas to `show_board` and to successful `draw_board` results so a completed AI drawing is visible immediately in compatible hosts; its UI refreshes through `get_board`. The MCP Apps SDK describes `updateModelContext` as a deferred, overwrite-only model context update and `sendMessage` as a conversation message that can trigger a follow-up; Doodle keeps those roles separate. Text-only hosts and plugin installs use the same tools and should call `show_board` after drawing when supported. See [Add UI to your MCP server](https://developers.openai.com/plugins/build/chatgpt-ui), [Package your plugin](https://developers.openai.com/plugins/build/plugins), [Developer commands](https://learn.chatgpt.com/docs/developer-commands), and [Submit desktop-only plugins](https://developers.openai.com/plugins/deploy/desktop-only).
